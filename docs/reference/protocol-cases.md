## Normal forwarding and protocol checks

**Problem statement.** A fault result is meaningful only after the same wiring, peers, VLANs and gateways have demonstrated correct service under ordinary conditions. Use these as behavioral acceptance checks. IEEE 802.1AX governs the aggregation visible to the LACP partner, IEEE 802.1Q covers bridging and spanning tree, and the RouterOS manual defines MikroTik's peer forwarding. The outage budgets above are lab service targets. [IEEE 802.1AX](https://standards.ieee.org/ieee/802.1AX/6768/) · [IEEE 802.1Q](https://standards.ieee.org/ieee/802.1q/10323/) · [RouterOS MLAG](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)

| ID | Smallest setup and exercise | Pass evidence |
| --- | --- | --- |
| BASE-01 | T1, cold boot then steady state. Bring up both peers and both client legs with matching keys within each local aggregate. Send several independent flows. | Each client selects the intended single aggregator, sees the expected partner system ID on both legs, and eligible legs reach collecting/distributing. Each selected conversation delivers once and in order in steady state. Demonstrate use of both legs across flows. Equal distribution of bytes is unnecessary. [Link aggregation](https://standards.ieee.org/ieee/802.1AX/6768/) |
| BASE-02 | T1, source one MAC first on VLAN 110, then use the same MAC on an isolated second VLAN. Probe learned unicast, unknown destination, and prohibited cross-VLAN L2 delivery. | Per-VID learning, expected tagged/untagged egress, learned unicast only where expected, and zero copies on the forbidden VLAN. A cold unknown destination may flood to eligible ports. Correlate FDB and witness capture. [VLAN bridges](https://standards.ieee.org/ieee/802.1q/10323/) |
| BASE-03 | T1, send marked broadcast and learned unicast to dual-attached destinations, first with both legs eligible and then with the local destination leg unavailable. | Normal local delivery, one eligible copy per endpoint and correct use of the peer port to reach a dual-attached destination through its surviving leg. Capture both client legs. Exercise the surviving path before restoring both legs. [RouterOS forwarding rules](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/) |
| BASE-04 | Small T4 with two independent inter-switch paths. Set a preferred root and costs, then allow the tree to settle. Repeat the steady-state check when two physical members instead form a single LACP trunk. | On the looped independent paths, the selected alternate discards user frames while processing the applicable BPDUs. On the LACP topology, STP sees the logical trunk. For MSTP, confirm roles and payload separately in every configured instance. [Bridged networks](https://standards.ieee.org/ieee/802.1q/10323/) · [RouterOS MLAG and STP](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/) |
| BASE-05 | T1 with VRRP gateway peers and an actual routed service. Verify IPv4 and, where configured, IPv6. Then separately withdraw the active router gracefully and remove it abruptly. | One active gateway per connected VRID/address family after election. Hosts resolve the VIP, reach the service through it, and receive replies on the proper VLAN. Compare adverts and takeover to the configured VRRP timer: an abrupt loss exercises the active-down interval, a graceful priority-zero advert exercises the skew timer. Score the service interruption independently. [VRRPv3 RFC 9568, sections 6.1 and 6.4](https://www.rfc-editor.org/rfc/rfc9568.html) · [RouterOS VRRP](https://manual.mikrotik.com/docs/cli-reference/interface/vrrp/) |
| BASE-06 | T2 then T3, run the distributed client matrix during steady state and again after each repair. Start fresh TCP sessions as well as retaining an established one. | All expected local, routed and cross-site services work in both directions. Denied L2 adjacency stays denied. Validate on-wire member use, zero unexpected copies, gateway ownership and no second gap after rejoin. This row is the design's end-to-end acceptance check. |

## vMotion, IP and MAC mobility

**Problem statement.** Moving an unchanged VM and transferring an IP to a new NIC change different tables. The first should move the bridge's MAC/VID entry. The second also requires neighbor caches to associate the IP with the new MAC. One observer can recover while another continues to use the old path.

Start each move with both stationary clients exchanging traffic with the old endpoint and with each other. Record the old mapping on each peer and at both clients. Capture the old and new attachment simultaneously. Record the last source frame on the old port, the first on the new port, the first correct FDB entry, and the first timely delivery **from each stationary client**. Do not allow two live copies of the mobile identity during an ordinary move. Restore by moving it back and score that direction as a separate event.

| ID | Move to perform | Decisive observation |
| --- | --- | --- |
| MOVE-01 | Same IP, MAC and VID. Move from an attachment on peer 1 to peer 2, then between two distinct dual-connected host bonds. Repeat with one GARP and, separately, one ordinary Ethernet source frame. | Both stationary senders recover within the M1 budget from the first valid source frame. The neighbor IP→MAC value stays constant. The FDB changes egress for that VID. No continuing delivery to the old port or unrelated witness. [Reported GARP and stale port](https://forum.mikrotik.com/t/mac-move-detection/271620) |
| MOVE-02 | Move that identity between the two sites on stretched VLAN 310, then return it. Compare an active move with a silent receiver. In the silent run suppress periodic GARP, ND and automatic replies until the marked first source frame. | Score the active run from the first new source frame. In the silent run, record behavior before the network had a chance to learn, natural ageing, and the time after the first source frame. Report each site's gap individually. A mistaken cross-site VLAN boundary is exposed by the baseline. [Inter-pair move reports](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137?page=6) |
| MOVE-03 | Transfer one IPv4 service IP to a **different MAC** on the opposite peer. Remove the IP from the old owner before enabling it on the new owner. Repeat with an ARP announcement and with fresh neighbor resolution. If IPv6 is deployed, repeat with an unsolicited Neighbor Advertisement with the applicable Override flag and with solicited resolution. | Check IP→MAC at the two clients and relevant gateways independently of MAC/VID→port at the switches. Report which table stayed stale and when each client could open a new connection. A new service owner can legitimately lose an established TCP session without application-state replication. [IPv4 announcements](https://www.rfc-editor.org/rfc/rfc5227.html#section-2.3) · [IPv6 neighbor updates](https://www.rfc-editor.org/rfc/rfc4861.html#section-7.2.5) |
| MOVE-04 | Keep the MAC fixed and renumber its IP on the same port, then reuse that MAC in a **different VLAN** on a second attachment. Use separate subnet addresses per VLAN. | IP renumbering alone leaves the original L2 egress valid. In the VLAN case each MAC/VID has its own egress and receives only its VLAN's traffic. Verify fresh connections to the new address and that the withdrawn address has no responding owner. This is a design control for false MAC-move diagnoses. |
| MOVE-05 | On an ESXi bench, live-vMotion a running VM with unchanged IP/MAC between two host uplinks while a persistent application session is active. Record the port-group **Notify Switches** setting, teaming policy, port/VLAN membership, and migration start/finish. | Capture the actual announcement on the new uplink. ESXi can emit **RARP (EtherType 0x8035)** on behalf of the VM. Verify the frame enters the MLAG peer, learning changes, the old attachment stops receiving learned unicast, and both local and remote clients recover. Separate the VM pause from post-announcement network loss. A Containerlab identity move exercises forwarding. This case records actual hypervisor behavior. [Broadcom Notify Switches and RARP](https://knowledge.broadcom.com/external/article/343401/ip-to-mac-mapping-garp-rarp-and-notify-s.html) · [Broadcom capture and stale physical-switch mapping](https://knowledge.broadcom.com/external/article/318873/a-virtual-machine-loses-network-connecti.html) |
| MOVE-06 | After a clean MOVE-01 or MOVE-02, move A→B→A inside one FDB ageing interval. In separate trials, move while one destination-side MLAG leg is down and move while a remote peer rejoins. Keep an unmoved host in the same VLAN under traffic. | Each latest valid source location wins. Capture any reversion after peer resync, the number and duration of gaps per client, and any loss on the stationary control. Require autonomous recovery without waiting for ageing or clearing FDB/ARP. [Repeated migration field observations](https://forum.mikrotik.com/t/mac-move-detection/271620) · [Remote rejoin case](https://forum.mikrotik.com/t/mlag-what-happens-when-member-interface-joins/263166) |

## MAC learning, peer forwarding and VLANs

| ID | Problem and evidence | Trigger and decisive observation |
| --- | --- | --- |
| M1 | A moved VM remained on its old bond despite captured GARP. Operators moving between pairs reported 5–10 minutes before recovery. [Proxmox MAC move](https://forum.mikrotik.com/t/mac-move-detection/271620) · [Inter-pair move](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137?page=6) | T1 then T3/VLAN 310. Warm one MAC on host A. Stop its old attachment, preserve MAC/IP/VID, start it on B and emit **one** source frame. Test ordinary unicast and GARP in separate runs. Repeat bond→bond and DC A→DC B→A. Defer the single-attached variant to [FUT-01](../cases/README.md#future-cases). Time first source at new ingress, new FDB mapping at each hop and first return packet. Require delivery within the declared move budget (proposed 1 s after source) and no packets to the old port after convergence. Keep a silent-move control to measure first learn versus natural ageing. |
| M2 | A VM could ping while its MAC disappeared from displayed host tables. Traffic reached an unrelated host. The reported Windows SET/static-bond environment differs from 802.3ad. [Hyper-V migration and captures](https://forum.mikrotik.com/t/crs317-mlag-hyper-v-set-vm-connectivity-failures-after-migration-and-pfsense-carp-events/273728) · [Flooding with apparently correct FDB](https://forum.mikrotik.com/t/strange-traffic-flooding-in-mlag-setup/271419) | T1. Validate actual SET/CARP behavior with those endpoints separately. |
| M3 | Reboot left a MAC on the peer port and reachability depended on the source host. A temporary static entry restored service. A peer-port entry can also be correct when the local leg is down. [Post-reboot observation](https://forum.mikrotik.com/t/mlag-transmit-hash-policy/274432/8) · [SUP-228131 and SUP-228515](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137/129) | T1/T2. Force one client leg down, forward through the opposite peer, restore, reboot each role separately and send from multiple sources. Compare expected next hop on **each** peer for the same MAC/VID. Pass when every source reaches the host via a valid path and an available local leg resumes local delivery without static entries. |
| M4 | A member flap reportedly caused a broad flush and CPU saturation with a stable root. Disabling an unrelated port has also stopped bridge traffic. [Four-switch report](https://forum.mikrotik.com/t/7-25-1-stable-is-released/274226/22) · [Unrelated port](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137/48) | Run §4. Compare FDB size before/during/after **and** track MACs continuously sourced on unaffected ports. Report CPU recovery, blast radius and duration. A smaller FDB alone cannot establish a forwarding outage. |
| M5 | VLAN-specific failures, FDB sync warnings and a missing peer-port VLAN can produce similar symptoms. A broadcast-flood setting explained an apparent regression in one stack. [Per-VLAN observation](https://forum.mikrotik.com/t/bridging-hosts-not-forwarding/270143) · [Operator correction](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137/115) · [7.25 changes](https://forum.mikrotik.com/t/7-25-stable-is-released/273987/1) | T1/T2. Add a VLAN to both peers under load. Use the same MAC on two isolated VLANs. In a control, omit only one VID from one peer trunk, then restore it. Force traffic across the peer. Check effective VLAN membership, per-VID FDB, ARP/ND and warning MAC/VID where supported. Healthy VLANs must continue and the repaired VLAN must relearn. Repeat with asymmetric broadcast flooding and correct it to establish the configuration signature. |
| M6 | Peer loss can drop a dual-connected host, and a packet may return to the dual-connected bond it entered. A historic reflection case ended when the operator removed a configuration that disabled offload. [7.25.2 fixes](https://forum.mikrotik.com/t/7-25-2-stable-is-released/274638) · [Reflection follow-up](https://forum.mikrotik.com/t/solved-mlag-problem-packets-occasionally-reflected-back/160701) | T1. Send distinguishable low-rate broadcast, unknown unicast, multicast and warmed unicast. Record at source, both client legs and the independent witness. Remove one leg, then one chassis. Each eligible endpoint receives exactly one copy, the originating bond receives no reflected copy, and the dual-homed destination on the survivor stays reachable. Repeat with opposite ingress. |
| M7 | Heartbeat timeouts, FDB notify-buffer warnings and watchdog reboots appeared after hours. Staff explained that remote local MACs replicated per interface and VLAN can legitimately multiply the row count. [CRS326 report and staff reply](https://forum.mikrotik.com/t/mlag-fdb-host-table-duplication/269518) · [Long-running degradation](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137/77) | T2. Step from a handful of hosts to about 100 across 33 VLANs, then to the intended deployment cardinality, within resource limits. Hold population fixed, cycle a subset of MACs and leave a quiet interval. Sample unique MAC/VID, local/static/dynamic/peer rows, free memory, CPU, heartbeat, warning rate and sentinel loss. Start with a 24 h soak and extend past any reported onset. Fail on unreachable sentinels, recurring session loss, watchdog, or sustained resource growth at fixed population. Recheck resource limits on the target switch. |

| L2 | Disabling a Linux client leg in Containerlab left traffic mapped to a failed bond, while disabling the switch port worked.
