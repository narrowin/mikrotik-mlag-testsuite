## Core and data-center outage matrix

**Problem statement.** “DC A failed” can mean a single switch, both cores, the DCI, or loss of every node and probe in A. Each event has different survivors. Test one event per row with an observer in the other site, and then reverse A and B. For every row, run failure and restoration as separate measurements.

Run DC-02, DC-03 and DC-06 with just the four cores and Linux endpoints first. Repeat them with local distribution and the CHR firewall VRRP pair in T3. The two-core-per-site wiring table predicts surviving **physical** DCI paths, and the probes establish which paths actually forward. [Two- and four-circuit failure matrix](../plans/two-site-design.md#what-the-extra-circuits-buy)

| ID | Fault to inject on T3 | Expected service and evidence |
| --- | --- | --- |
| DC-01 | Lose A1 alone, then A2 alone from baseline. | The client and the local service host both use the surviving distribution switch. B local controls stay clean. Verify VIP delivery through the surviving path. |
| DC-02 | Lose C1 alone, then C2 alone. Repeat on D1, then D2 in site B. Keep the failed core down through the observation period. | The surviving core handles A↔B and access-to-core service within budget. Local services behind surviving access stay up even while the failed core is absent. On rejoin check both directions and every hash path. [Reported dependency on the failed core returning](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137/100) |
| DC-03 | Lose one inter-site member, restore it, then cut the whole DCI while all four local peer links remain up. | One surviving DCI member should carry cross-site traffic. Full DCI loss isolates VLAN 390 into two islands, which can each elect an active firewall. Keep both access-local Layer 2 controls running. On heal, verify a single owner, a valid virtual-MAC location and stable VIP delivery. |
| DC-04 | Lose **both C1 and C2** together while access A remains powered. Restore a single core first, then its peer. | A’s access-local Layer 2 control can stay up. A loses its VIP path and the DCI. B’s local firewall can own the VIP. Measure when the first eligible core restores A’s VIP path and whether second-core rejoin interrupts it. |
| DC-05 | Stop **all of DC A**, including access, cores, firewall, service and clients. Keep B and its observer running. Restore A core-first, then repeat access-first on a fresh run. | B keeps its access-local flow and its firewall owns the VIP after any election. A-only service and cross-site flow are expected down. Measure the returning VIP path and any failback. Score application relocation only if a separately specified replica exists. |
| DC-06 | Crossed loss: remove C1 and D2. Compare two-wire and four-wire DCI. Then remove C1 and D1 in a separate run. | With the two straight DCI wires, C2 and D1 have no surviving cross-link in the crossed case. With four wires C2–D1 survives. Same-index loss leaves C2–D2 in both variants. Predict the path before pulling links, check local service in both sites, and verify cross-site success exactly where a path exists. |
| DC-07 | Rolling return from a disconnected site or pair. Rejoin secondary first, primary first and both simultaneously on the pinned development build. | Timestamp physical/virtual links, peer establishment, STP if active, LACP IDs, VRRP ownership and first stable VIP delivery. Confirm no second outage on the healthy site's local flow. Run a mixed-version upgrade rehearsal only if separately requested. |

## Cases that require physical devices or a specific partner

**Problem statement.** CHR exercises RouterOS software MLAG. It cannot establish Prestera forwarding behavior, optical carrier timing or the forwarding capacity of a particular CRS. Promote findings from CHR to a bench with the actual switch pair, partner model and RouterBOARD firmware where these determine the outcome. Hardware-offloaded bridging and L3 hardware offload are distinct. The RouterOS manual requires disabling **L3 hardware offload for the whole switch** when using MLAG. [RouterOS platform limits](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)

| ID | Problem | Physical or partner-specific test |
| --- | --- | --- |
| H1 | CRS8xx tagged frames have been looped back. Changing bridge offload could restart MLAG. A second bridge or a split-horizon setting explained poor performance or reflection in other reports. [CRS8xx fix](https://forum.mikrotik.com/t/7-24-6-long-term-is-released/274207) · [Offload restart fix](https://forum.mikrotik.com/t/7-25-2-stable-is-released/274638) · [Solved throughput case](https://forum.mikrotik.com/t/solved-extremely-low-bandwidth-in-sfp28-mlag-setup/165580) | On the target CRS, record bridge-port H flags, chip/port placement, CPU load and RouterBOARD firmware. Replay M2/M6 and P3 with wire-side capture. Toggle supported L2 offload on a bench port and measure peer session and data. Require no reflected frame, intact forwarding and the expected steady-state offload. |
| H2 | At realistic host counts, a CRS CPU can exhaust FDB notification resources. Timing under CPU starvation and physical link-down do not transfer from a VM. [CRS326 case](https://forum.mikrotik.com/t/mlag-fdb-host-table-duplication/269518) · [CRS317 storage-traffic report](https://forum.mikrotik.com/t/crs317-1g-16s-on-ros-7-22-2-heavy-cpu-after-mlag-bonding-for-proxmox-server/270148) | Repeat M4/M7, P1 and DC-02 at intended host/VLAN count and traffic. Use actual power removal, optical pull and one-way fault in separate runs. Capture externally, with the observer on a separate power source. Report maximum outage and resource trend for that model and build. |
| H3 | Partner implementations affected system-ID renegotiation, return to service and in-band management. [Catalyst case](https://forum.mikrotik.com/t/mlag-configuration-for-v7-22-1/269918) · [HP stack management loss](https://forum.mikrotik.com/t/mlag-issue-with-lacp-ports-on-hp-5130-stack/165500) · [Hyper-V SET/CARP](https://forum.mikrotik.com/t/crs317-mlag-hyper-v-set-vm-connectivity-failures-after-migration-and-pfsense-carp-events/273728) | Replay L1–L4, M1 and G1 on the deployed switch/server/firewall type. For switch-independent teaming, explicitly model the actual teaming mode, one active source location and failback. Check both in-band management IPs and routed applications. Attribute a partner-specific result to the tested combination. |

### Additional tests when the service uses these features

| ID | Problem | Experiment and pass condition |
| --- | --- | --- |
| X1 | An early report flagged IGMP snooping. It gives little detail about membership or the querier. [Snooping report](https://forum.mikrotik.com/t/mlag-hopelessly-broken/167137/11) | T1. Supply a querier, a joined receiver and an unjoined witness per side. Join, leave, age and move the receiver across a peer failure. Compare membership reports, bridge multicast database and payload with the unsnooped control. A current subscriber receives one copy. With known membership, the same stream stays off a nonmember host port unless policy calls for flooding. |
| X2 | RouterOS 7.25 changes how MVRP works on dual-connected bonds. Statically allowed VLANs do not exercise registration. [7.25 release](https://forum.mikrotik.com/t/7-25-stable-is-released/273987/1) | T2. Register one dynamic VLAN, carry traffic through each peer, then withdraw it. Record registrar state, effective membership and first/last delivered frame. Repeat during failover. Pass when the intended VLAN becomes usable and its withdrawal leaves other VLANs intact. |
| X3 | In a stacked-tag PPPoE deployment the discovery request reached the server, but its offer disappeared on the return path. [Stacked-tag report](https://forum.mikrotik.com/t/crs326-with-mlag-and-bridge-vlan-filtering-with-qinqinq/174002) | On a matching service path, capture discovery (PADI/PADO) and session establishment at both edges, both trunk legs and peer. Compare tag order, EtherType and length to a single-tag control. Repeat M1 and a member loss. Require complete discovery, a working session and correct tags in both directions. |
| X4 | Windows domain controllers reportedly failed RPC replication while ping and iperf worked. The report establishes an application symptom and leaves the cause open. [RPC field report](https://forum.mikrotik.com/t/routeros-7-11-2-mlag-with-2-crs317-1g-16s-rpc-errors/170599) | If this workload matters, put a representative client and service on opposite peers. Run a known-good transaction on T0, repeat on T1 through fault and rejoin, and retain the application result and packet trace. Score the transaction against its service deadline. Require evidence of the first missing or misdelivered packet before attributing an application failure to MLAG. |
