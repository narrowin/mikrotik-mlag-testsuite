In the linked post 137, Larsa explained that the topology was client-specific and invited narrower questions. Neither post gives a topology, fault sequence, or loss measurement. **Software for new runs.** At the start of each campaign, resolve the newest upstream releases of Containerlab, Networka, NUTS, the endpoint image and its tools, and any optional traffic generator in use. Use the updated Networka checkout if it is newer than the packaged release. Use the latest RouterOS **development** release for the entire campaign. It was **7.26beta7** on 24 November 2026. Record what actually ran, including version, Git revision for a checkout, image digest and architecture. The older versions named in field reports identify where symptoms were seen. ### Which tool does what?

**Problem statement.** We need to read several switches while a fault is present and measure the packet gap during the same event. Those operations run on different clocks.

| Tool | Fit for this lab, checked 24 November 2026 |
| --- | --- |
| **Networka** (`nw`) | The runner sends every RouterOS command through Networka, and operators use it for pre-fault, held-fault or post-recovery state checkpoints. The runner depends on **0.3.0** from PyPI. v0.2.0 saved eight read-only command outputs per CHR in about one second on the small lab. [Verified lab commands](../operator-guide.md#collect-a-networka-checkpoint) · [Networka releases](https://github.com/narrowin/networka/releases/latest) |
| **NUTS**, Network Unit Testing System | A pytest/Nornir network test runner. It can query devices through its test classes and assert expected outcomes. Reuse our Linux and RouterOS reachability assertions on the current release (**3.6.0** at review). The repository's runner recipe still specifies an older release and includes a local NAPALM RouterOS patch. Check one positive and one negative assertion on the refreshed runner before trusting a fault verdict. [Upstream NUTS](https://github.com/network-unit-testing-system/nuts) · [Current package](https://pypi.org/project/nuts/) |

Containerlab's latest published release at review was **0.83.0**. Recheck the publishers at launch. Save the resolved RouterOS channel, Containerlab version, Networka revision, NUTS version and client-tool versions next to each run. [Containerlab releases](https://github.com/srl-labs/containerlab/releases/latest)

### How other teams test failover

**Problem statement.** A successful ping after a planned change gives no record of which client lost packets, whether they went to another port, or whether a second outage occurred on restoration.

| Who tested what | What their evidence establishes | What to carry into this lab |
| --- | --- | --- |
| Nokia, 7750 SR OS MC-LAG with pseudowire redundancy | Nokia inspects operational state and selected members on the two PEs, forces a switchover, and explicitly clears the forced state. The guide demonstrates role and path selection. It publishes no per-client interruption duration for our topology. [Nokia worked example and forced switchover](https://documentation.nokia.com/acg/25-3-2/books/interface-configuration-classic/c008-mc-lag.html) | Write down the forwarding path before the change and after restoration. Capture each peer’s selection and prove the expected path with data. Apply RouterOS’s own forwarding rules. |
| SONiC, multi-chassis LAG and dual top-of-rack switch tests | Its MC-LAG tests change member, peer-link and chassis availability and check traffic. In the separate dual-ToR suite, engineers run upstream or downstream traffic with the fault as an action, check switch roles, and use packet identities to report consecutive gaps and duplicates. A field issue documents VLAN flooding being counted as duplicates by the test. [MC-LAG tests](https://github.com/sonic-net/sonic-mgmt/blob/master/tests/mclag/test_mclag_l3.py) · [Live link-failure tests](https://github.com/sonic-net/sonic-mgmt/blob/master/tests/dualtor_io/test_link_failure.py) · [Gap and duplicate analysis](https://github.com/sonic-net/sonic-mgmt/blob/master/tests/common/dualtor/dual_tor_io.py) · [Flooding investigation](https://github.com/sonic-net/sonic-mgmt/issues/8272) | Keep independent streams in each direction, group consecutive misses per stream, and distinguish extra copies reaching a bystander from duplicate delivery to the intended receiver. |
| MikroTik operators, CHR client-leg loss and Proxmox migration | One operator ran a series of pings and compared disabling the client NIC with disabling the router port. Another captured the VM’s gratuitous ARP after a real migration while investigating a stale MAC location. [CHR client-leg experiment](https://forum.mikrotik.com/t/mlag-client-lacp-failover-handling/272065) · [Proxmox migration capture](https://forum.mikrotik.com/t/mac-move-detection/271620) | Record which side changed and whether carrier actually fell. Date a MAC move to the first valid source on the new port. Observe the old port while its link is still up. |

**Consecutive events.** Start continuous numbered traffic that represents the case, an independent control stream, and per-port captures. Establish a clean baseline. Apply one event, record its actual time, and keep sending. Check both peers’ bridge, RSTP, LACP and per-VLAN MAC state alongside the first missing or misdirected frame. Include VRRP adverts and a routed transaction when a gateway is on the measured path. Before applying the next event, require ten timely replies from each affected client and the expected forwarding state. Score restoration separately while the same streams continue. If service stays down, record the open-ended outage before changing anything else. [IETF failover and reversion metrics](https://www.rfc-editor.org/rfc/rfc6414.html) · [Local run with six continuous streams](../../results/2026-11-24-small-lab/README.md)
