## Cases

### MLAG bond member loss and return · STP off

Takes client 1's bond member to CHR 1 (ether3) down at both ends, holds it down for 8 s, then brings both ends back up. Run it with `mlag-lab run --case bond-member-loss`.

| Phase | Expected | Limit | Run 1 |
| --- | --- | --- | --- |
| Member down | Carrier drops at both ends, so CHR 1's MLAG bond client1 (mlag-id=11) stops using ether3 and client 1 sends only on its member to CHR 2. | ≤ 3 s | ✅ PASS · up to 0.21 s (1 probe) |
| Member back | Carrier returns at both ends and LACP renegotiates ether3 with client 1 at the 1-second LACPDU rate. | ≤ 3 s | ✅ PASS · 2.39 to 2.60 s (24 probes) |

- **Member down:** Carrier drops at both ends, so CHR 1's MLAG bond client1 (mlag-id=11) stops using ether3 and client 1 sends only on its member to CHR 2. CHR 1 forwards traffic for client 1 over the peer link (mlag-peer-port ether2) to CHR 2, which delivers it on its member of the same MLAG bond, with brief loss. [Source](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)
- **Member back:** Carrier returns at both ends and LACP renegotiates ether3 with client 1 at the 1-second LACPDU rate. Each end carries traffic on the member only once its LACP flags show synchronization, collecting and distributing (S, C, D), so the return causes at most brief loss. [Source](https://manual.mikrotik.com/docs/cli-reference/interface/bonding/monitor-slaves/)
- **MikroTik fixes this case checks:** Packets looped back to a dual-connected bond ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); LACP system ID not synchronised when bonds are created before MLAG ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG))

### Silent host past bridge ageing, then relearn · STP off

Sets ageing-time=10s on the bridge of both MLAG peers and reads it back, and pins permanent neighbour entries between the MAC-move host and both traffic hosts, so no host needs ARP while one side is silent. After the baseline it drops every frame the MAC-move host sends for 25 s, with a tc filter on egress of both its bond members, then removes the filter and watches 5 s of return plus a 3 s recovery window. Afterwards it restores ageing-time=5m, reads it back and removes the pinned neighbour entries. Run it with `mlag-lab run --case mac-age-relearn`.

| Phase | Expected | Limit | Run 1 |
| --- | --- | --- | --- |
| Host silent | Nothing from the MAC-move host reaches either MLAG peer. | ≤ 26 s | ✅ PASS · 24.94 to 25.01 s |
| Host sends again | The host's first frame enters CHR 1 on ether5, so CHR 1 learns the host MAC on ether5 and CHR 2 on the peer port. | ≤ 1 s | ✅ PASS · up to 0.09 s |

- **Host silent:** Nothing from the MAC-move host reaches either MLAG peer. After the 10 s ageing time both peers remove the host MAC from the bridge host table: CHR 1 its entry on ether5, CHR 2 its entry on the peer port ether2. Frames to the host MAC are then unknown unicast, so both peers flood streams 101 and 102 to the other traffic host as well. This is correct bridge behaviour and is recorded, not failed. Every stream to or from the host loses probes for the whole silence; that loss is the fault itself, so the limit is the 25 s silence plus the 1 s relearn target. Stream 302 and both bypass streams lose nothing. [Source](https://manual.mikrotik.com/docs/cli-reference/interface/bridge/)
- **Host sends again:** The host's first frame enters CHR 1 on ether5, so CHR 1 learns the host MAC on ether5 and CHR 2 on the peer port. Lab target, measured from the host's first frame at a CHR TAP: flooding of streams 101 and 102 to the other traffic host stops within 1.0 s, streams 101, 102, 201 and 202 deliver again within 1.0 s and lose nothing afterwards. The field report saw this flooding continue while both bridge host tables showed the right port. Stream 302 and both bypass streams lose nothing. [Source](https://forum.mikrotik.com/t/strange-traffic-flooding-in-mlag-setup/271419)
- **MikroTik fixes this case checks:** Packets looped back to a dual-connected bond ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); LACP system ID not synchronised when bonds are created before MLAG ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG))

### Repeated MLAG bond member flap · STP off

Takes client 1's bond member to CHR 1 (ether3) down at both ends for 1 s and back up for 3 s, five times, then watches 8 s of return plus a 3 s recovery window. Both MLAG peers' bridge host table entries for client 2 and the MAC-move host are sampled every 0.35 s throughout. Run it with `mlag-lab run --case member-flap-repeat`.

| Phase | Expected | Limit | Run 1 |
| --- | --- | --- | --- |
| Five member flaps | Each flap removes ether3 from CHR 1's MLAG bond client1 and adds it back once LACP renegotiates. | ≤ 3 s | ✅ PASS · 2.61 to 2.82 s (105 probes) |
| Member back after the fifth flap | Carrier returns for the last time and LACP renegotiates ether3 with client 1 until it shows synchronization, collecting and distributing (S, C, D). | ≤ 3 s | ❌ FAIL · 2.40 to 2.61 s (24 probes) · [failed check](01-member-flap-repeat/result.json#L585) |

- **Five member flaps:** Each flap removes ether3 from CHR 1's MLAG bond client1 and adds it back once LACP renegotiates. While the member is down, CHR 1 forwards traffic for client 1 over the peer link to CHR 2, with brief loss. This phase runs from the first flap to the fifth return, so it holds four complete flaps and the fifth down; result.json lists the loss of every flap separately. Each loss of streams 101, 201 and 302 may last at most 3 s, the member limit per flap. Streams 102 and 202 never touch client 1 and lose nothing, and the bridge host table entries for client 2 and the MAC-move host stay on both MLAG peers. The field report saw unrelated MACs move to the peer port after a member flap. [Source](https://forum.mikrotik.com/t/7-25-1-stable-is-released/274226/22)
- **Member back after the fifth flap:** Carrier returns for the last time and LACP renegotiates ether3 with client 1 until it shows synchronization, collecting and distributing (S, C, D). Loss of streams 101, 201 and 302 lasts at most 3 s. Streams 102 and 202 and both bypass streams lose nothing, and the host entries for client 2 and the MAC-move host stay present. [Source](https://manual.mikrotik.com/docs/cli-reference/interface/bonding/monitor-slaves/)
- **MikroTik fixes this case checks:** Packets looped back to a dual-connected bond ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); LACP system ID not synchronised when bonds are created before MLAG ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG))
