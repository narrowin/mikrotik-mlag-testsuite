## Cases

### MAC move between MLAG peers and back · STP off

Switches the MAC-move host's active-backup bond from its link to CHR 1 to its link to CHR 2, keeping the same MAC and IP address, then switches it back after 4 s. Run it with `mlag-lab run --case mac-move`.

| Phase | Expected | Limit | Run 1 | Run 2 | Run 3 |
| --- | --- | --- | --- | --- | --- |
| Move to CHR 2 | The host's gratuitous ARP enters CHR 2 on ether5, a regular bridge port without mlag-id. | no loss | ✅ PASS · no loss | ✅ PASS · no loss | ✅ PASS · no loss |
| Move back to CHR 1 | The host's gratuitous ARP enters CHR 1 on ether5. | no loss | ✅ PASS · no loss | ✅ PASS · no loss | ✅ PASS · no loss |

- **Move to CHR 2:** The host's gratuitous ARP enters CHR 2 on ether5, a regular bridge port without mlag-id. CHR 2 moves the host MAC to ether5 in its bridge host table and floods the broadcast to its local ports and over the peer port; CHR 1 floods it only to its regular port ether5 and moves the MAC to the peer port ether2. Lab target: no probe to or from the host is lost, and once the gratuitous ARP reaches CHR 2, no frame addressed to the host MAC leaves CHR 1 on ether5.
- **Move back to CHR 1:** The host's gratuitous ARP enters CHR 1 on ether5. CHR 1 moves the host MAC back to ether5 and floods the broadcast to its local ports and over the peer port; CHR 2 floods it only to its regular port ether5 and moves the MAC to the peer port ether2. Lab target: no probe to or from the host is lost, and from the moment the gratuitous ARP reaches CHR 1 to the end of the recovery window, no frame addressed to the host MAC leaves CHR 2 on ether5.
- **MikroTik fixes this case checks:** Packets looped back to a dual-connected bond ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); LACP system ID not synchronised when bonds are created before MLAG ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); MLAG MAC address handling for ageing, flushing and moving ([7.24](https://cdn.mikrotik.com/routeros/7.24/CHANGELOG)); MAC moving between regular ports and bonds ([7.22](https://cdn.mikrotik.com/routeros/7.22/CHANGELOG))

### Peer link loss and return · STP off

Cuts the peer link (ether2) at both MLAG peers, holds it down for 15 s, restores it and watches 65 s of return. Run it with `mlag-lab run --case peer-link-loss`.

| Phase | Expected | Limit | Run 1 | Run 2 | Run 3 |
| --- | --- | --- | --- | --- | --- |
| Peer link down | Both MLAG peers lose ICCP and leave mlag-state connected. | ≤ 5 s | ✅ PASS · no loss | ✅ PASS · no loss | ✅ PASS · no loss |
| Peer link back | ICCP returns to mlag-state connected on both peers and the secondary takes the shared system ID again. | ≤ 5 s | ✅ PASS · no loss | ✅ PASS · no loss | ✅ PASS · no loss |

- **Peer link down:** Both MLAG peers lose ICCP and leave mlag-state connected. With mlag-lacp-fallback=yes the MLAG secondary stops using the shared system ID, so the clients renegotiate LACP and keep their member to the primary, with brief loss. [Source](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)
- **Peer link back:** ICCP returns to mlag-state connected on both peers and the secondary takes the shared system ID again. The clients renegotiate LACP with brief loss. [Source](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)
- **MikroTik fixes this case checks:** Packets looped back to a dual-connected bond ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); LACP system ID not synchronised when bonds are created before MLAG ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); New settings mlag-lacp-fallback and mlag-init-delay ([7.25](https://cdn.mikrotik.com/routeros/7.25/CHANGELOG)); mlag-heartbeat; no peer port reset on heartbeat timeout, a warning is logged ([7.18](https://cdn.mikrotik.com/routeros/7.18/CHANGELOG)); MLAG connection after a peer link flap (introduced in 7.13) ([7.14](https://cdn.mikrotik.com/routeros/7.14/CHANGELOG))

### Repeated MLAG bond member flap · STP off

Takes client 1's bond member to CHR 1 (ether3) down at both ends for 1 s and back up for 3 s, five times, then watches 8 s of return plus a 3 s recovery window. Both MLAG peers' bridge host table entries for client 2 and the MAC-move host are sampled every 0.35 s throughout. Run it with `mlag-lab run --case member-flap-repeat`.

| Phase | Expected | Limit | Run 1 | Run 2 | Run 3 |
| --- | --- | --- | --- | --- | --- |
| Five member flaps | Each flap removes ether3 from CHR 1's MLAG bond client1 and adds it back once LACP renegotiates. | ≤ 3 s | ❌ FAIL · 2.50 to 2.71 s (106 probes) · [failed check](01-member-flap-repeat/result.json#L545) | ❌ FAIL · 2.60 to 2.81 s (104 probes) · [failed check](02-member-flap-repeat/result.json#L591) | ❌ FAIL · 2.49 to 2.70 s (102 probes) · [failed check](03-member-flap-repeat/result.json#L545) |
| Member back after the fifth flap | Carrier returns for the last time and LACP renegotiates ether3 with client 1 until it shows synchronization, collecting and distributing (S, C, D). | ≤ 3 s | ❌ FAIL · 2.29 to 2.49 s (23 probes) · [failed check](01-member-flap-repeat/result.json#L597) | ❌ FAIL · 2.29 to 2.50 s (23 probes) · [failed check](02-member-flap-repeat/result.json#L551) | ✅ PASS · 2.29 to 2.50 s (23 probes) |

- **Five member flaps:** Each flap removes ether3 from CHR 1's MLAG bond client1 and adds it back once LACP renegotiates. While the member is down, CHR 1 forwards traffic for client 1 over the peer link to CHR 2, with brief loss. This phase runs from the first flap to the fifth return, so it holds four complete flaps and the fifth down; result.json lists the loss of every flap separately. Each loss of streams 101, 201 and 302 may last at most 3 s, the member limit per flap. Streams 102 and 202 never touch client 1 and lose nothing, and the bridge host table entries for client 2 and the MAC-move host stay on both MLAG peers. The field report saw unrelated MACs move to the peer port after a member flap. [Source](https://forum.mikrotik.com/t/7-25-1-stable-is-released/274226/22)
- **Member back after the fifth flap:** Carrier returns for the last time and LACP renegotiates ether3 with client 1 until it shows synchronization, collecting and distributing (S, C, D). Loss of streams 101, 201 and 302 lasts at most 3 s. Streams 102 and 202 and both bypass streams lose nothing, and the host entries for client 2 and the MAC-move host stay present. [Source](https://manual.mikrotik.com/docs/cli-reference/interface/bonding/monitor-slaves/)
