## Cases

### Baseline readiness · RSTP

Applies the bridge mode on both MLAG peers, waits for MLAG and LACP to settle, checks MLAG, LACP and the virtual links, and sends numbered pings for 4 s without a fault. Run it with `mlag-lab run --case baseline`.

| Phase | Expected | Limit | Run 1 |
| --- | --- | --- | --- |
| Steady state | Both MLAG peers show mlag-state connected, one as MLAG primary and one as MLAG secondary, and use the primary's system ID as the shared system ID. | no loss | ✅ PASS · no loss |

- **Steady state:** Both MLAG peers show mlag-state connected, one as MLAG primary and one as MLAG secondary, and use the primary's system ID as the shared system ID. Each client bonds both members and every probe arrives once. [Source](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)
- **MikroTik fixes this case checks:** Packets looped back to a dual-connected bond ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); LACP system ID not synchronised when bonds are created before MLAG ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); MLAG peer stuck in the disabled state after config changes ([7.25](https://cdn.mikrotik.com/routeros/7.25/CHANGELOG)); MLAG state permanently disabled after changing bridge settings ([7.22](https://cdn.mikrotik.com/routeros/7.22/CHANGELOG)); Priority setting to elect the MLAG primary ([7.17](https://cdn.mikrotik.com/routeros/7.17/CHANGELOG))

### MLAG primary reboot · RSTP

Resets the bridge on CHR 1 and CHR 2 over management SSH with the bridge mode of the run, picks the MLAG peer that reports mlag-state connected as primary, and after a loss-free baseline reboots it with `/system reboot` (1 s delay). The runner waits for the guest uptime to reset, then keeps probing for 16 s plus a 3 s recovery window. Run it with `mlag-lab run --case primary-reboot`.

| Phase | Expected | Limit | Run 1 |
| --- | --- | --- | --- |
| Primary down | The MLAG secondary reverts its MLAG bonds to its own LACP system ID (mlag-lacp-fallback=yes) and both traffic hosts renegotiate LACP, with brief loss. | ≤ 5 s | ✅ PASS · 2.91 to 3.12 s |
| Primary back | The rebooted peer keeps its bond members out of the bond until the MLAG system ID syncs (mlag-init-delay), rejoins as MLAG primary and restores the shared system ID. | ≤ 5 s | ✅ PASS · up to 0.21 s |

- **Primary down:** The MLAG secondary reverts its MLAG bonds to its own LACP system ID (mlag-lacp-fallback=yes) and both traffic hosts renegotiate LACP, with brief loss. The virtual links keep carrier, so each host drops its member to the primary only at the LACP short timeout (3 × 1 s). The secondary's edge MLAG bonds keep forwarding throughout. [Source](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)
- **Primary back:** The rebooted peer keeps its bond members out of the bond until the MLAG system ID syncs (mlag-init-delay), rejoins as MLAG primary and restores the shared system ID. Both traffic hosts renegotiate LACP to the shared system ID, with brief loss. [Source](https://manual.mikrotik.com/docs/high-availability-solutions/multi-chassis-link-aggregation-group/)
- **MikroTik fixes this case checks:** Dual-bond hosts dropped when an MLAG peer is lost ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); Packets looped back to a dual-connected bond ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); LACP system ID not synchronised when bonds are created before MLAG ([7.25.2](https://cdn.mikrotik.com/routeros/7.25.2/CHANGELOG)); New settings mlag-lacp-fallback and mlag-init-delay ([7.25](https://cdn.mikrotik.com/routeros/7.25/CHANGELOG))
